# Source Record Provenance in `stitch` with Seed-First Ingestion and LLM-Ready Envelope

## Summary

Persist a required provenance envelope on every newly ingested OGSI source in this repo, expose it only through a new source detail endpoint, and update only `seed` plus the shared API/client/model layers in this phase. `stitch-llm` remains a consumer for now, but the persisted envelope must be designed now to support a later phase where LLM-created sources/resources are POSTed with full audit context.

The original `SourceRecord` idea is close, but it should be generalized before landing. The main change is to avoid ETL-specific field names so the same envelope cleanly supports provider rows, static seed JSON, Faker-generated records, and future LLM audit payloads.

The new requirement can be immediate. Do not worry about backwards compatibility
with existing clients or ETL processes

## Key Changes

### `SourceRecord` design
- Replace the ETL-centric shape with a generalized envelope:
  - `record_id: str | None`
  - `run_id: str | None`
  - `observed_at: datetime`
  - `producer: str`
  - `payload: arbitrary JSON-compatible value`
- Add `kind: Literal["provider", "seed_static", "seed_faker", "llm_audit"]`
  - This avoids ambiguity without needing separate schema variants.
- Define field semantics now:
  - `record_id`: identifier of the original input record when one exists.
  - `run_id`: identifier for the producing run/job/request batch when one exists.
  - `observed_at`: timestamp when the original source record or audit artifact was observed/generated by the producer.
  - `producer`: stable producer identity including version when available.
    - Use a versioned identity string rather than a bare version.
    - For seed, use a value like `stitch-seed@<version>` derived from the installed seed package version.
    - For later LLM POSTs, this should identify the LLM service version/build that produced the audited payload.
  - `payload`: exact source/audit content to retain for later inspection.
- Keep `source_record_hash` derived from stable JSON serialization of `payload` only.

This shape is better for future LLM POSTs because the full foundry prompt/response audit object fits naturally into `payload`, while `kind`, `producer`, and `run_id` describe how it was created without pretending it came from an external provider row.

### Shared model + API contract
- Add `SourceRecord` to the shared OGSI source model layer and require it on source ingestion.
- Extend all ingestible source variants to accept `source_record`.
- Keep normal read models lightweight:
  - create/list/get source responses omit `source_record`,
  - source detail returns processed source fields plus `source_record` and `source_record_hash`.
- Make this strict now:
  - `POST /oil-gas-field-sources/` requires `source_record`,
  - `POST /oil-gas-fields/` requires `source_record` on each newly created source in `source_data`.
- Add `GET /oil-gas-field-sources/{id}/detail`.
- For now, raw `source_record` visibility follows the same source-level license check as processed source data.
  - If a caller is licensed to view the source row, they may view the raw stored envelope from the detail endpoint.
- Keep `GET /oil-gas-fields/{id}` and `GET /oil-gas-fields/{id}/detail` lightweight; callers use source ids from `source_data` to fetch source detail on demand.

### Persistence
- Add `source_record` as a `NOT NULL` JSON column on `oil_gas_field_sources`.
- Add `source_record_hash` as a `NOT NULL` string column on `oil_gas_field_sources`.
- Persist the envelope exactly as received after model validation.
- Compute hash from canonical JSON serialization of `source_record.payload` only.
- Update source create/get/detail conversion logic so:
  - write paths persist the envelope and hash,
  - lightweight read paths exclude it,
  - detail read paths include it.

### `seed` deployment
- Do not modify existing static seed JSON files.
- For static seed payloads:
  - treat each source object loaded from file as the `source_record.payload`,
  - have the seed process construct the rest of the envelope at runtime,
  - use `kind="seed_static"`,
  - use `producer` equal to the installed `stitch-seed` package version string,
  - set `record_id` to `None` unless a stable source id can be derived safely from existing JSON,
  - set `run_id` from a generated per-run identifier created by the seed process,
  - set `observed_at` at ingestion time.
- For Faker-generated payloads:
  - have `source_record.payload` contain enough information to reproduce or audit the generated record, not just the final normalized source row.
  - include:
    - the generated source object actually posted,
    - the seed configuration relevant to reproduction,
    - the effective random seed and per-record sequence/index,
    - the selected source discriminator.
  - use `kind="seed_faker"`,
  - use `producer` equal to the installed `stitch-seed` package version string,
  - set `run_id` to the generated per-run identifier,
  - set `record_id` to a deterministic record label such as the run id plus item index,
  - set `observed_at` when the record is generated.
- The seed process becomes responsible for wrapping every source in `source_record` before POSTing, regardless of whether the source came from static JSON or Faker.

### `stitch-llm` scope in this phase
- Do not implement source/resource POST creation yet.
- Do not change `stitch-llm` request/response behavior yet unless shared client/model updates require fixture refreshes.
- Design future compatibility explicitly:
  - when `stitch-llm` later creates sources/resources, it should submit `source_record.kind="llm_audit"`,
  - `payload` should hold the full auditable artifact, including prompt context, model request payload, model response payload, selected value, rationale, citations, and any request metadata worth preserving,
  - `producer` should identify the deployed LLM service version/build,
  - `run_id` should group related LLM outputs when applicable,
  - `record_id` can identify a single LLM suggestion/audit artifact when useful.
- Keep the current `FieldSuggestionResponse` shape unchanged in this phase; the plan only ensures the future POST path has a clean provenance envelope to target.

## Test Plan

- Model tests:
  - `source_record` is required on source ingestion.
  - `kind` is required and validated.
  - `payload` accepts arbitrary JSON-compatible data.
  - `record_id` and `run_id` may be `null`.
- DB/action tests:
  - `source_record` and `source_record_hash` persist and round-trip through source detail.
  - hash depends only on `payload`.
  - resource creation persists envelopes for newly created source rows.
- API tests:
  - source/resource POSTs reject missing `source_record`.
  - normal source create/list/get responses omit `source_record`.
  - source detail includes `source_record` and hash.
  - field detail remains lightweight and still exposes source ids.
- Seed tests:
  - static seed records are wrapped at runtime without editing fixture files.
  - Faker records produce `source_record.payload` with reproduction/audit metadata.
  - `producer` comes from package version resolution.
  - a per-run id is assigned consistently across a seed execution.
- Verification runs:
  - focused API router/model/db tests,
  - `make seed-test`,
  - targeted shared client/model tests that need fixture updates.

## Assumptions

- This phase still excludes ETL repo changes and excludes implementing LLM POST creation.
- The API contract becomes strict now even though some future producers are not yet updated.
- `producer` is intended to carry versioned producer identity; for seed this is package version, and for future LLM writes it should be service/build identity.
- Concretely, store `producer` as a versioned identity string such as `stitch-seed@0.1.0`, not a bare version like `0.1.0`.
- Keeping `payload` as the exact auditable artifact is preferable to forcing one normalized internal schema across ETL, seed, and LLM producers.
- Local DB reset remains acceptable after the schema change.
- No separate permission layer is introduced yet for raw provenance payloads; source detail access controls are sufficient in this phase.
